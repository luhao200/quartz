## 前置准备

开始一个新项目时，完成以下规范化工作：

- **文件命名**：统一命名规范
- **文件架构**：分析并规划目录结构，编写 `.gitignore`、`CMakeLists.txt`
- **文件编码**：代码文件统一使用 UTF-8
- **版本控制**：建立 Git 仓库，规划分支策略

## 前期调研

- **input**：产品想法、项目需求
- **output**：对产品/项目的概念理解、技术路线初步方案

### 新产品调研

将自己对产品的大致想法描述给 AI，重点确认：

- 产品优缺点与可行性
- 各功能对应的技术路线和实现工具
- 遗漏的细节

**工具**：ChatGPT、Gemini

### 新功能调研

分析现有代码架构，重点关注与新功能相关的代码和资源（如硬件原理图）。

**工具**：CodeX、Claude Code、Qoder

---

## 需求分析

- **input**：简易需求（一句话描述 + 关键约束）
- **output**：详细需求文档 `requirements.md`

### 优化简易需求

将简易需求优化为结构化的简要需求文档 `briefrequirements.md`。

| 场景  | 工具                            |
| --- | ----------------------------- |
| 新产品 | 使用提示词优化插件                     |
| 新功能 | Augment / Qoder 优化提示词         |

### 需求详细化

将 `briefrequirements.md` 展开为 `requirements.md`。

| 场景  | 工具与方式                                                                                 |
| --- | ------------------------------------------------------------------------------------- |
| 新产品 | ChatGPT、Gemini、Deep Research                                                          |
| 新功能 | **CodeX**：Plan 模式 / `briefrequirement_to_requirement` 命令                              |
|     | **Claude Code**：Plan 模式 / `briefrequirement_to_requirement` 命令（积极使用`AskUserQuestion`） |
|     | **Qoder**：Spec 功能                                                                     |

关键动作：

1. **循环讨论**：反复细化实现细节、测试方法等
2. **AI 交叉验证**：用不同模型/工具对同一需求进行审查，避免单一模型盲区

### 需求审批

对 `requirements.md` 进行最终审查和修正。

| 场景  | 工具                              |
| --- | ------------------------------- |
| 新产品 | ChatGPT、Gemini                  |

## 编码执行

- **input**：`requirements.md`
- **output**：代码 + Git 提交

### OpenSpec 流程

按以下三步执行：

1. **openspec-proposal**：`requirements.md` → OpenSpec 工程（拆解任务与方案）
2. **openspec-apply**：OpenSpec 工程 → 代码实现
3. **openspec-archive**：OpenSpec 工程 → 归档并 Git 提交

### Issues CSV 流程（可选）

适用于需要精细化进度跟踪的场景。

**核心思路**：将完整需求拆解到 CSV 中，逐条执行开发 → 自动测试 → Review → Git 提交。

**CSV 结构要求**：

| 字段     | 说明                         |
| ------ | -------------------------- |
| 标题     | 任务简述                       |
| 内容     | 具体开发内容，明确边界，防止任务跑偏         |
| 测试验收要求 | 可执行的验收标准                   |
| Review要求 | 代码审查标准                   |
| 开发进度   | 开发完成状态                     |
| 初次Review | 开发过程中逐项 Review 的结果       |
| 回归Review | 所有任务完成后的回归测试结果           |

**工作方式**：

1. 让 CodeX CLI 逐条确认开发内容、完成开发、自动测试、Review，自动提交到 Git
2. 全部完成后，针对 Issues 做回归测试和 Review，查漏补缺
3. Issues CSV 作为代码的一部分提交到仓库，便于跟踪任务进度

## 核心原则

1. **勤提交**：Git 提交要频繁，不要等"完整功能"才提交。做好分支规划，写清提交信息。
2. **不绑定单一工具**：工具 A 解决不了的问题，换工具 B 往往能很快解决。
3. **交叉验证**：重要结论用不同模型/工具交叉确认。
4. **精确表述**：与 AI 沟通要详细、准确。能提供可验证信息就提供——例如"将字号**从 12** 改为 13"比"把字号调大一点"更有效。
5. **维护上下文文档**：记录文件功能、关联及接口，帮助模型理解项目，减少 token 消耗。
6. **善用软链接**：当项目依赖另一个项目库时，在 `reference/` 文件夹下软链接其代码。
